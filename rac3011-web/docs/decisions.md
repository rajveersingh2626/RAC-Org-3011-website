- 2026-09-04: Sidebar groups Overview/Reporting/Club/Me are shown to every authenticated user except items that name a permission (Reporting requires `reports:submit`; Club → Events requires `club_events:log`, Showcase requires `showcase:submit`). Admin items each require exactly one permission key.
- 2026-09-04: `TagInput` at `maxTags` keeps its text input enabled (adds are refused in `add()`) rather than disabling it, so Backspace can still remove a tag. Disabling it trapped keyboard users at the cap.

- 2026-09-04: `Badge` green/amber/red/blue hexes are new: the Design System only defines the neutral and pink families. Light+dark pairs were chosen to match existing token contrast and are centralised in one `toneClass` map.

- 2026-09-04: `Chip`'s remove affordance is a nested `role="button"` span (button-in-button is invalid HTML), so a chip with `onRemove` exposes two buttons and the outer accessible name reads "Tag Remove Tag".
- 2026-09-04: `InlineStatus` ok-state green is not in tokens.css, so it uses arbitrary values with a theme-scoped variant rather than one hex that fails a theme.
- 2026-09-04: `ImageSlot` shares one dashed cream panel for the empty and error states, differentiated by `data-state="empty"|"error"`; error shows a lucide `ImageOff` mark at low opacity with the fixed caption "Photo unavailable".
- 2026-09-04: `Table` renders the 2px accent rule on `thead` from `md:` and on each `tr` below `md:` (where `thead` is hidden), so stacked rows still read as separated groups.
- 2026-09-04: `Timeline` conveys state via `data-state`, `aria-current="step"` and an `sr-only` prefix, never colour alone; items default to `todo`.
- 2026-09-04: `RadialGauge`/`ProgressBar` expose the clamped visual percentage as `data-pct` while `aria-valuenow`/`aria-label` carry the uncapped true figure (mockup: the ring must not cap at 100%).
- 2026-09-04: `Pagination`'s page-window algorithm (exported as `paginationRange`) always keeps page 1, the last page, and `page-1..page+1`, collapsing any remaining gap into a single `…`; totals of 7 or fewer render every page with no ellipsis. The mockup only shows one static example (`1 2 3 … 7`); this rule reproduces it and generalises without a magic breakpoint per dataset size.
- 2026-09-04: `Stepper` has no mockup section (not in the Design System doc). Built to match `Timeline`'s established state language exactly: `data-state` of `done`/`current`/`todo`, `aria-current="step"` on the current item only, and an `sr-only` state prefix so state is never colour-only. Numbered circles (not dots, since steps are ordinal) use a filled accent circle with a `lucide-react` `Check` for done, an accent-outlined circle with the numeral for current, and a neutral-outlined circle for todo; a `Step X of N` eyebrow caption (9px/700/uppercase, matching the mockup's other eyebrow captions) sits above the row.
- 2026-09-04: `SideNav`'s "support for hiding items" (per the task brief) is implemented as caller-side omission, not a `hidden` prop: a group renders nothing when its `items` array is empty, and there is no visibility logic inside the component. This matches the brief's own constraint that `SideNav` "does NOT know about routing or permissions" — `PortalShell` filters `groups`/`items` before passing them in.
- 2026-09-04: `SideNav`'s background is always `bg-portal-bar` (dark) regardless of `[data-theme]`, matching both the Sidebar mockup (identical dark panel drawn once, not twice per theme) and the existing decision that "the portal bar... was always dark."
- 2026-09-04: `ThemeToggle`'s icon shows the *current* theme (Sun in light mode, Moon in dark mode) rather than the theme it will switch to, since no mockup covers this control; `aria-pressed` mirrors `theme === 'dark'` for the same reason.
- 2026-09-04: `/__ui` (`UiKitPage`) wraps itself in a local `UiKitProviders` (`ThemeProvider` + `ToastProvider` only), not the app's full `Providers`. `Providers` already wraps every route once via `App.tsx`, so nesting it again on this page would double-fetch `/me` through a second `AuthProvider` and stand up a redundant `QueryClientProvider`/`ToastProvider` pair for a page with no data-fetching or auth-gated primitives. `ThemeProvider` and `ToastProvider` are kept because `ThemeToggle` and `Toast`/`useToast` need real context to render as themselves rather than stubs. One consequence: because there is a single shared `ThemeProvider` for the whole page, the two `ThemeToggle` instances (one per light/dark panel) reflect and control the *same* global preference — clicking either one flips the real app-wide theme, which is expected given there's normally only one `ThemeToggle` instance in the app chrome.

The outer page shell itself is pinned to `data-theme="light"` as a neutral default since it sits outside both panels.

- 2026-09-04: The axe smoke suite (`e2e/smoke.spec.ts`) surfaced real, pre-existing accessibility bugs, fixed rather than suppressed: (1) `tokens.css`'s base resets (`html`, `body`, `a`, `::selection`, `:focus-visible`, reduced-motion) were bare CSS outside any `@layer`, so per the CSS Cascading Layers spec they beat every Tailwind utility class regardless of specificity — `a { color: var(--accent) }` silently overrode every `text-white/NN` utility on an anchor site-wide (this is why `PublicFooter`'s nav links rendered pink-on-dark at 3.58:1 instead of the intended near-white). Fixed by wrapping those resets in `@layer base { ... }`. (2) `PublicFooter`'s column headings used theme-variable `text-accent` on a footer that is *always* dark regardless of page theme, so in light-mode pages they rendered light-mode pink (`#D81B60`, 3.58:1) on the dark footer; switched to the fixed `text-pink-bright` token (`#F0407F`, 4.85:1) that already matches dark theme's `--accent`. (3) The footer copyright line was `text-white/40` (3.79:1); bumped to `/62` (~7:1). (4) Added a `--danger-fg`/`text-danger-fg` token pair: `--danger` in dark theme (`--color-maroon-dark #7A1024`) was designed as a background/border color, not text-on-dark-background — every `text-danger` error message (Field, Radio, Alert, InlineStatus, Menu destructive, FileUpload) read at ~1.57:1 in dark theme. `--danger-fg` reuses the same lighter red (`#E58B98`) `Stat.tsx` had already established ad hoc for its "down" delta in dark theme; light theme is unchanged (`--danger-fg: var(--danger)`, already passing). (5) `TagInput`'s input had `aria-expanded`/`aria-controls` without `role="combobox"` (axe `aria-allowed-attr`) — added the role to match `Combobox`/`MultiSelect`; `TagInput.test.tsx` queries updated from `getByRole('textbox')` to `getByRole('combobox')` accordingly. (6) `ProgressBar`'s visible `label` was never wired to the `role="progressbar"` element's accessible name (axe `aria-progressbar-name`); added `aria-labelledby` pointing at the label span, with an `aria-label="Progress"` fallback when no label is passed. (7) `Chip`'s remove affordance was a `role="button"` span nested inside the chip's own `<button>` — invalid nested-interactive HTML/ARIA (axe `nested-interactive`). When `onRemove` is given, `Chip` now renders a plain (non-interactive) `<span>` wrapper containing a real `<button>` for remove, instead of an outer `<button>` containing a fake one; the toggle/`selected` `<button>` shape is unchanged when `onRemove` is absent. One consequence: a `Chip` with both `onRemove` and an `onClick` (via the rest-prop passthrough) no longer forwards `onClick` to anything, since the outer element is no longer a button — removable chips were never meant to double as click targets. (8) `/__ui`'s own demos for `Select` and `RangeInput` had no `aria-label` (axe `select-name`/`label`) — both components already support `aria-label` passthrough; the showcase page was just missing it.

Use Node 22 locally until msw ships a Node 24-compatible `@mswjs/interceptors`.

## Reporting (spec step 4)

- 2026-09-04: "Current reporting month" (`currentReportMonth`, `src/lib/reports/month.ts`) is always the previous calendar month — clubs file a report for the month that just ended, matching the mockup's "August report isn't in yet" copy seen in September.
- 2026-09-04: The `clubs`-type field (collaborating clubs) and every admin club/zone picker (Admin Clubs overview zone filter, Ad-hoc request audience) reads `GET /public/clubs` instead of the authenticated `GET /clubs`. A president/secretary's `clubs:view` grant is scoped to their own club only (`§4.4` seed), so the authenticated list would return just one club and make "who else was involved" unusable; the public route returns every club's public summary and needs no permission.
- 2026-09-04: Report-request "questions" are plain free-text prompt strings (`CreateReportRequestDto.questions: string[]`, verified against the real DTO), not typed fields as the mockup's rows imply. Club-side answers are stored as `{ "0": "...", "1": "..." }`, keyed by question index, matching the API's `answers: Record<string, unknown>`.
- 2026-09-04: Report Form Builder reorders fields with up/down `IconButton`s, not drag-and-drop — the spec explicitly allows either ("drag handles or up/down buttons") and the ground rules forbid adding a UI library or a new drag dependency for one screen.
- 2026-09-04: Admin Clubs overview renders only compliance essentials (club, filed date, activity count, status, query action) and omits the mockup's per-activity aggregate columns (collaborators list, people-reached total) — those require the points/aggregation engine (step 5, not yet built) to compute correctly; showing an ad hoc client-side sum here would silently disagree with the real scoring once it ships.
- 2026-09-04: `/portal/admin/clubs/:clubId/:month` (Score Month, `reports:score`) is left as `ComingSoon`. Scoring a report is `PATCH /clubs/:id/points`, which lives in the points module — only a port stub (`src/points/adapters`) has landed on the API side, no controller. Building the screen now would mean shipping a form with nowhere real to submit.
- 2026-09-04: `/portal/dashboard` ships only the report-status widget (this month's status via `Stat`/`Badge`, matching the explicit ask) behind a real `GET /reports?filter[clubId]&filter[month]` call. The full role-aware `ClubDashboard`/`OfficerDashboard` (points trend, per-category split, district announcements) is not built — it depends on the points engine and the announcements module, neither of which exist yet on the API side. Non-reporting accounts see a plain `EmptyState` explaining the same.
- 2026-09-04: The report-activity `link` field (photo) always uses `FileUpload`'s `dynamic` storage tier, not `private` — a private-tier file streams through an RBAC-checked backend route rather than resolving to a public URL, which doesn't fit "attach a photo that gets you into the showcase."
- 2026-09-04: `LinkFieldControl`/`FileUpload` instances for the `link` field type are given a real string `label` (the field's own label) instead of being wrapped in the shared `Field` component like every other field type — `Field` renders a `<label for=...>` tied to a single control id via context, which `FileUpload` doesn't consume (it owns its own hidden `<input type="file">` id/label). Wrapping it in `Field` anyway left the file input with no accessible name at all (axe `label`, critical) since `FileUpload`'s own `label` prop was never passed; passing the field label to both would have produced two visible labels for one control.
- 2026-09-04: `OpenRequestsPanel`'s "Answered" badge is session-only, not server-verified — the API has no `GET` for a club's own response to a report request (`PUT /report-requests/:id/responses/:clubId` is upsert-only, write-side), so there is no way to know on page reload whether a request was already answered. Recorded as an operational/API gap, not something the frontend can work around.
- 2026-09-04: The officer-side AI assist panel (`ReportDetailPage`, gated on `reports:score`) is built against the real `GET /reports/:id/assist`. If the server's `ANTHROPIC_API_KEY` isn't configured, the endpoint still returns `200 {summary:'', suggestions:[]}` by design (`AnthropicAssistAdapter`), and the panel shows "The assist service isn't configured on the server yet" rather than an error — this is an operational gap (missing env var), not a code gap.
- 2026-09-04: `e2e/reporting.spec.ts` reuses the existing club-officer e2e session (`e2e_session=1` cookie + `me.json`) for both member and admin reporting routes, rather than adding a second cookie value/identity to the shared mock server. `me.json`'s grants gained `reports:review` (zone scope) and `requests:manage` (none scope) alongside the existing `reports:submit` — a small, realistic widening (a president who's also a district officer) that avoids touching the shared session/cookie logic in `mock-api.ts` while a second agent was concurrently editing that same file for the public-site routes.
- 2026-09-04: The mock API's in-memory report/query store (`e2e/mock-api.ts`) is shared across all three Playwright projects (mobile/tablet/desktop), which run in parallel. The one interactive test that performs an irreversible mutation (replying to `rep_queried`'s open query, which flips its status server-side) is guarded with `test.skip(testInfo.project.name !== 'desktop-1440', ...)` so it runs exactly once; every axe-smoke visit is read-only and safe to repeat across projects.

## Caching and performance (spec §14)

- 2026-09-05: Cloudflare edge cache rule (L1, §14.1) created via API on zone `rotaract3011.org` (`http_request_cache_settings` phase, ruleset id `6fde959d45af402d8cd28111a73881c9`, rule id `e4da97f2b335499aaee8fc3e0379a8a1`): matches `api.rotaract3011.org` + `/public/*`, `cache: true`, `edge_ttl.mode: respect_origin`, bypasses when a `rac3011.session` cookie is present. Verified live: repeat anonymous requests to `/public/home` return `cf-cache-status: HIT`; the same request with a session cookie present stays `DYNAMIC` every time.
- 2026-09-05: `GET /public/live` (§14.2's split-out visitor counter) doesn't exist on the API yet. `useLiveVisits` (`src/lib/publicApi/live.ts`) calls it directly and only falls back to reading `visits` off `/public/home` on a 404; any other error surfaces normally (no silent double-fallback). `home.ts`'s `visits` field is now `.optional()` since the API will eventually stop sending it. `useVisitOnce`'s `POST /public/visits` result now writes into the live-visits query cache (`['public','live']`), not the home query, since that's the field's new home.
- 2026-09-05: TanStack Query persistence (§14.6) only ever persists `['public', ...]` queries to `localStorage` (`shouldPersistQuery`, `src/app/providers.tsx`), explicitly excluding the live-visits poll. Chose this over persisting the whole cache indiscriminately: authenticated data (`['me']`, reports, etc.) staying in-memory-only means `signOut()`'s existing `removeQueries` call remains a complete wipe — persisting private data into `localStorage` would leave it readable after logout on a shared machine until the next deploy's `buster` overwrote it. This is the more conservative reading of an otherwise-unspecified scope for "Persisted cache".
- 2026-09-05: The `Persister` for `@tanstack/react-query-persist-client` is a small hand-written `localStorage` wrapper (`src/lib/queryPersister.ts`) rather than pulling in `@tanstack/query-sync-storage-persister` — the task's package list named only `@tanstack/query-persist-client-core` + the React wrapper, and the `Persister` interface (`persistClient`/`restoreClient`/`removeClient`) is three trivial methods; adding a third package for it wasn't justified.
- 2026-09-05: `index.html`'s new `<link rel="preconnect">`/`dns-prefetch` to the API origin is a hardcoded literal (`https://api.rotaract3011.org`), not a `%VITE_API_ORIGIN%` build-time placeholder — tried the placeholder first, but Vite's `htmlEnvHook` hard-fails the build (`URI malformed`) whenever that env var isn't defined for the build (true for a plain local `npm run build` with no `.env`), which would break the mandatory pre-push local build step. The literal matches the CSP's own hardcoded `connect-src https://api.rotaract3011.org` in `nginx.conf` — this app only ever talks to one real API origin regardless of which frontend hostname serves it.
- 2026-09-05: Route-level code splitting (§14.6) is done at the *surface* boundary, not by lazy-loading individual public pages within a surface. `App.tsx` now `React.lazy`s all six surface entry points (`main`, and the five subdomains) behind one `<Suspense>`; each surface's own module (`main.routes.tsx`, `mission3011.routes.tsx`, ...) still eagerly imports its own pages, so "public routes stay eager" holds *within* the resolved surface's chunk (no per-page waterfall once that chunk starts loading). ### 14.9 Prerendered public pages (built 2026-09-05)

- **Approach**: a post-build Playwright pass (`scripts/prerender.ts`), not `vite-plugin-ssg`. It starts `vite preview` (via the `vite` JS API, port 0) against the already-built `dist/`, crawls each route in `scripts/prerenderRoutes.ts` with a real Chromium page (`@playwright/test`'s `chromium`, already a dev dependency - no new package), waits for network idle, then captures `page.content()` (the live, post-render DOM) plus a dehydrated TanStack Query snapshot pulled via `window.__RAC_DEHYDRATE__` (exposed from `src/app/providers.tsx`/`src/app/prerender.ts`). The snapshot is inlined as `window.__RAC_PRERENDERED_STATE__` in a `<script>` before the module script, and `main.tsx` calls `hydrateRoot` instead of `createRoot` when `window.__RAC_PRERENDERED__` is set (`isPrerendered()`), so the browser reuses the server-rendered DOM instead of a client re-render flash. `createQueryClient()` (`providers.tsx`) calls `hydratePrerenderedState()` before anything renders, so first paint reuses that data; the existing `staleTime: 5min` still revalidates in the background exactly as before. Chosen over `vite-plugin-ssg`/`@prerenderer`: this app's routing already resolves per-hostname (`resolveSurface`, `src/app/host.ts`), so a plugin that assumes one route tree per build would need the same crawl-the-built-SPA workaround anyway; driving it directly with the already-installed Playwright is less surface area.
- **Route scope**: only the 18 static, unparameterized main-surface public routes (`scripts/prerenderRoutes.ts`). Excluded: `:slug`/`:category`/`:clubSlug` detail routes (unbounded - would need a full entity crawl from the API, a materially bigger and riskier scope not covered by the four required test routes), `/resources/sister-club` (`RequireAuth`-gated, §4.8: nothing behind auth may be prerendered), and the DRR calendar `ComingSoon` placeholders (no real backend, nothing to snapshot). Deferred, noted for a future task if it's wanted: prerendering detail pages would need the build to fetch the full `/public/projects`, `/public/past-drrs` etc. lists and fan out per slug.
- **`/` is special**: this app serves all six hostnames (`main` + 5 project subdomains) from the *same* built `dist/` via client-side `resolveSurface(window.location.hostname)` - nginx has always had one `server_name _` block with no host-based routing (`nginx.conf`). Baking main's home page into `dist/index.html` would ship the wrong content to every subdomain's `/` once they're cut over (§11.3 - not live yet, only `testing.rotaract3011.org` is wired today, confirmed via the Oracle Dokploy app record, so this isn't yet a live bug, but would become one at cutover without this fix). Fix: `/` prerenders to a separate `dist/home.html`, and `nginx.conf` gained a `map $host $spa_root_index` (`index.html` by default, `home.html` for the known main-surface hostnames) consumed only by a new `location = /` block; every other path is unaffected. `vite.config.ts` gained a matching `configurePreviewServer` plugin hook (`servePrerenderedRoot`) purely so local `vite preview` / the Playwright e2e suite can verify `/` the same way production nginx will - `vite preview` has no host-based routing at all.
- **Data snapshot / graceful degradation**: `src/lib/prerenderDegradation.ts`'s `isDegraded()` watches every `/public/*` response (and `requestfailed` event) captured during a route's crawl; if any failed, that route's HTML is simply not written (nginx's existing `try_files ... /index.html` fallback then serves the plain SPA shell for that one path - no separate "shell copy" needed). A total API-origin outage degrades every route the same way, uniformly, with no special-cased pre-flight check. Verified locally both ways: `VITE_API_ORIGIN=http://127.0.0.1:19999 npx tsx scripts/prerender.ts` (port nothing listens on) produced `0/18 public routes prerendered` with a warning per route and exit code 0; a plain `npm run build` with no `VITE_API_ORIGIN` set at all (the existing local-dev default) also degrades cleanly (`VITE_API_ORIGIN not set - shipping the plain SPA shell for every public route`). Neither run touched `dist/*.html` beyond the original `index.html`, and neither failed the build.
- **`/public/live` never baked in**: the crawl intercepts and aborts `**/public/live` and `**/public/visits` (`page.route(...).abort()`) for every route, so the visitor-counter widget is captured mid-loading-state (renders its own `—` placeholder, per `HomePage.tsx`) rather than a real, soon-stale number, and `useVisitOnce`'s `POST /public/visits` never fires during a build (it would otherwise double-count a real visit per build run). Known, accepted residue: `/public/home`'s own payload still has a legacy `visits.count` field (§ decision above, "the API will eventually stop sending it") which *is* part of the dehydrated `['public','home']` query snapshot we deliberately bake in - so that stale count is present as inert JSON inside the `__RAC_PRERENDERED_STATE__` script tag, just never rendered as visible text. This matches the same characteristic the existing `localStorage` persistence already has for that field; not treated as a new problem to solve here.
- **Staleness**: prerendered HTML is a build-time snapshot - a content update (e.g. an admin publishing a new showcase project) won't change the shipped HTML until the next deploy. The client-side TanStack Query layer still revalidates in the background on hydrate per the existing `staleTime: 5min`, so a visitor sees corrected data within one round trip even between deploys; only the very first paint can show build-time-stale content. Deliberately **not building**, per the task: a content-publish webhook that triggers a rebuild on every admin edit would close this gap; left as a documented follow-up, not implemented.
- **CI incident, found and fixed same day**: the first push (`7eff58d`) hung the GitHub Actions build for over an hour instead of failing. Root cause, reproduced locally with `docker build`: (1) `Dockerfile`'s build stage was `node:22-alpine` (musl libc) - Playwright's bundled Chromium does not support musl at all, so `chromium.launch()` in `scripts/prerender.ts` always threw `Executable doesn't exist`; (2) that throw happened on the line between `startPreviewServer()` and the script's own `try/finally`, so the already-listening `vite preview` HTTP server was never closed - a live server keeps Node's event loop alive forever, so the process (and the whole `npm run build` chain, and the CI job) hung rather than exiting, even though `main().catch(...)` did log the warning. Fixed: `Dockerfile`'s build stage is now `node:22-bookworm-slim` (glibc) with `RUN npx playwright install --with-deps chromium` before `npm run build` (final `nginx:alpine` stage is untouched - only the build stage's browser-launch capability changed, final image size unaffected); `scripts/prerender.ts` now wraps `chromium.launch()` inside the same `try/finally` chain that closes the preview server, and `main()`'s outer promise chain ends in `.finally(() => process.exit(0))` as a deliberate safety net so a future leaked handle of this class can never hang the build again. Verified with a local `docker build --platform linux/arm64` (matching the Blacksmith ARM64 runner): the happy path now prerenders 18/18 routes inside the container in ~21s against a reachable mock API, and the no-`VITE_API_ORIGIN` degrade path completes in ~6s with the expected warning - both exit cleanly. - **Second CI incident, found deploying the fix above**: the fixed image built (~2 min) and deployed, but `curl`ing the live site still returned the plain 883-byte shell for every route. CI's own build log showed `0/18 public routes prerendered` with no hang - a silent, "successful" degrade. Cause: `scripts/prerender.ts`'s crawl runs inside a *real Chromium browser*, and the real API's CORS policy (`app.enableCors({ origin: env.WEB_ORIGINS, credentials: true })`, `rac3011-api/src/main.ts`) only trusts the real web hostnames, not `vite preview`'s ephemeral `http://localhost:PORT` origin - every `/public/*` fetch from the crawling page was browser-blocked before `isDegraded()` ever saw a real API problem. This never showed up locally because `e2e/mock-api.ts` (used for every local/CI-adjacent test) echoes a permissive `Access-Control-Allow-Origin` for any origin - the mock server's own convenience masked the exact gap that only the real API's strict policy exposes. Fixed with a `page.route(`${API_ORIGIN}/**`, proxyPastCors)` handler (registered before, so overridden by, the `/public/live`/`/public/visits` aborts) that re-issues the request through Node's own `fetch()` - which has no CORS enforcement, since CORS is a browser-only mechanism - and re-fulfills the browser's request with the real response plus an `Access-Control-Allow-Origin` echoing the request's own `Origin` header (a wildcard `*` is rejected outright once `credentials: 'include'` is in play, which `src/lib/api.ts`'s `apiFetch` always sets) and `Access-Control-Allow-Credentials: true`, plus a matching `OPTIONS` preflight response. This is the same trust boundary a real SSR server would sit inside; it doesn't touch the API's CORS config or weaken it for real browsers. Verified against the real `https://api.rotaract3011.org` (not the mock) both via an isolated repro script and the real `scripts/prerender.ts`: `18/18 public routes prerendered`, with real content (e.g. real club names from `/public/clubs`) confirmed in the output HTML.

## Scroll restoration (all 6 surfaces)

- **Root cause of the "wonky/inconsistent" navigation Rahul reported: none of the 6 independent `createBrowserRouter()` trees (`main`, `mission3011`, `drishti`, `rcl`, `careerbridge`, `ride`) rendered react-router's `<ScrollRestoration />`.** React Router v7 data routers do not reset scroll on client-side navigation, and don't restore prior scroll on back/forward, unless `<ScrollRestoration />` is mounted somewhere in the tree. Confirmed via `grep -rn "ScrollRestoration" src/app` returning nothing before this fix. Short pages never showed the bug (nothing to scroll), which is exactly why it read as "inconsistent" rather than "broken everywhere."
- **Fixed by adding one root-level `RouteObject` per router** (`element: <><ScrollRestoration /><Outlet /></>`, `children: <the router's existing top-level routes array>`), rather than sprinkling it per-page - `ScrollRestoration` only needs to exist once anywhere in a given router's rendered tree, and a single root wrapper is the standard v7 placement. Applied identically across `main.routes.tsx` (wrapping the existing `RequireAuth`/`PortalLayout`/`AdminLayout` tree) and the 5 simpler surfaces (`mission3011`, `drishti`, `rcl`, `careerbridge`, `ride`), including the 3 (`rcl`/`careerbridge`/`ride`) whose per-route `<Layout>{children}</Layout>` wrapping isn't itself Outlet-based - the new root wrapper nests above that flat routes array regardless, since it's a plain react-router nesting concern, independent of how each page's own `Layout` renders internally.
- **No `getKey` or other `ScrollRestoration` config was added.** This app's "prerendering" (`scripts/prerender.ts`) snapshots a real headless-browser DOM after client rendering (via Playwright), not a `renderToString` SSR pass, and `src/main.tsx` only switches between `hydrateRoot`/`createRoot` based on that snapshot - there's no server-rendered-HTML-vs-client scroll-restoration race specific to this setup that the plain default doesn't already handle correctly. No `scroll-behavior: smooth` (or any `scroll-behavior`) exists anywhere in `src` (checked `src/index.css`, `src/styles/tokens.css`, and a repo-wide grep), so there's no jarring animated-scroll interaction to guard against either - the default `<ScrollRestoration />` was used as-is, per the task's own "don't over-engineer" guidance.
- **Verified the fix causally, not just that tests stayed green:** a throwaway Playwright spec (scroll `/leadership` down, click the header nav's "Heritage" link, assert new-page `scrollY`) was run three times - once with the fix (passed, landed at `scrollY: 0`), once with `main.routes.tsx`/`publicMain.routes.tsx` stashed back to their pre-fix state (failed, landed at `scrollY: 325` after starting from `370` - i.e. reproduced Rahul's exact complaint), then once more with the fix restored (passed again). The scratch spec was deleted before committing; it isn't part of the permanent suite.

None of the three required pages includes a teams-admin/approvals view, so there's no specified workflow for who moves a team to `confirmed`; treating it as league-admin-only (set via a future admin surface or directly via `PATCH /rcl/teams/:id`, not built here) avoids inventing an unspecified confirm/withdraw workflow on the club's own page.
- **Fixtures page inline-result UX: a `Modal` per fixture (`FixtureResultModal`), triggered by an "Enter result"/"Edit result" button on each list row**, mirroring `SurgeryMoveModal`'s pattern (modal-driven mutation triggered from a list row) rather than an inline expandable row - the result form has 7 fields (2×runs/wickets/overs + notes) which reads better in a modal than inline in a list row, especially at the 390px viewport. "New fixture" uses the same modal pattern as `CampsPage`'s "Log a camp" button, gated on `subdomain:rcl:manage` scoped to `{type:'project', id:'rcl'}` (same scope-key convention as `mission3011`/`drishti`).
- **Fixtures are sorted client-side by `scheduledAt` ascending**, unlike standings. The spec's "don't re-sort client-side, trust server order" instruction is stated only for standings (where server order *is* the ranking); for fixtures the spec just says "sorted by date" with no equivalent instruction, so a defensive client-side chronological sort was added in `FixturesPage.tsx` in case the backend's default order differs.
- **Test organization matches this codebase's existing convention: pure-function `.test.ts` files only, no page-level component tests.** Checked `src/pages/mission3011/*.tsx` and `src/pages/drishti/*.tsx` - neither has `.test.tsx` siblings; page/component behavior is covered by Playwright e2e instead (`e2e/rcl.spec.ts`). Three new pure modules got unit tests: `src/lib/rcl/format.test.ts` (NRR signed-2dp formatting), `src/lib/rcl/roster.test.ts` (15-player cap + at-least-one-player validation), `src/lib/rcl/result.test.ts` (winner computation, including the spec's own 150/5-beats-120/8 acceptance example).

## Career Bridge subdomain

- **Built against the real `rac3011-api` Career Bridge controllers/DTOs** (`src/subdomains/careerbridge/*` in the sibling repo), which implement a full email-verification flow (`pending_email` → poster clicks an emailed link → `pending` → admin verifies/rejects → `verified`/`rejected`; `verified` → `filled`/`expired`) rather than the simpler single-step "post → admin decides" the original task brief described. A `/verify` route (`VerifyEmailPage.tsx`) was added beyond the brief's literal 5-route list (`/`, `/opportunities`, `/opportunities/:id`, `/post`, `/admin`) because without it there is no way for a visitor to complete the flow the API actually requires - it reads the `?token=` query param, calls `POST /public/careerbridge/listings/verify`, and shows a plain success/error state.
- **New client modules**: `src/lib/careerbridge/types.ts` (shared zod schemas for both public and admin shapes), `src/lib/publicApi/careerbridge.ts` (browse/detail/submit/verify - all unauthenticated), `src/lib/careerbridge/api.ts` (admin list/get/review/stats, authenticated). Split matches the API's own public-vs-manage controller split, not an arbitrary file boundary.
- **`OpportunitiesPage`/`OpportunityDetailPage` cards and layout follow `ShowcasePage.tsx`'s public card-grid pattern** (chip filters, `Card` inside a `Link`, `EmptyState`/`ErrorState`/`Skeleton` for the three query states) rather than `Table`, since this is a public browse surface, not an authenticated admin list - `CareerbridgeAdminPage`'s review queue instead reuses `Mission3011AdminPage.tsx`'s `CampReviewCard` pattern (one card per pending item, inline approve/reject with a reason modal for reject), since that page *is* the authenticated manage surface.
- **Honeypot field (`website`) is a raw, unlabelled `<input>` positioned off-screen via inline styles** (`position:absolute; left:-9999px; top:-9999px; width:1px; height:1px; overflow:hidden`), not the existing `VisuallyHidden` primitive (`sr-only` - CSS-clip based, meant for legitimate screen-reader-only content) and not `display:none`/`visibility:hidden` (per the task's own instruction, since some bots skip filling fields hidden that way). It carries `tabIndex={-1}` (removes it from the natural tab order) and `aria-hidden="true"` (screen readers skip it entirely) but has no `<label>`/`Field` wrapper, so it's never announced or focusable via normal navigation, while still being present in the DOM and submitted as `website` in the POST body exactly like every other field.
- **The public detail page's contact-email "reveal" button is a plain `useState` toggle, not a second network request.** The API already returns `contactEmail` in the public `GET /public/careerbridge/listings/:id` payload (no separate reveal endpoint exists, and Career Bridge listings are meant to be contacted, unlike Drishti's PII), so the button is pure UI friction against casual scraping, not a real access boundary - documented identically on the API side.
- **e2e persona (`e2e/fixtures/me.json`) gained `"subdomain:careerbridge:manage": [{ "type": "project", "id": "careerbridge" }]`**, following the same precedent as `subdomain:drishti:manage`/`subdomain:rcl:manage` already on this fixture. This means the e2e suite exercises the *positive* admin flow (verify a pending listing) rather than a negative "admin unreachable" test like `mission3011.spec.ts`'s - RBAC denial for `subdomain:careerbridge:manage` is proven at the API layer (`test/careerbridge.e2e.ts` in the sibling repo), matching how `subdomain:drishti:manage` is also only positively exercised here.
- **`e2e/mock-api.ts`'s `POST /public/careerbridge/listings` mock returns an extra `_testVerifyToken` field** (underscore-prefixed, mock-only) alongside the real `{id, status}` contract, since the real flow emails the token and Playwright has no email inbox to read. The e2e test that exercises the full post → verify → admin-queue path reads this field directly from the intercepted response rather than inventing a fake email step.

## RIDE subdomain (spec §10 step 14-17)

- **Built against the real `rac3011-api` RIDE controllers/DTOs** (`src/subdomains/ride/*` in the sibling repo, built in the same session), including the points-engine integration (`RideHostingAdapter`) and the exact public-vs-authed route split: `/public/ride/incoming` and `/public/ride/gallery` are unauthenticated, `/ride/support-clubs`, `/ride/delegations`, `/ride/delegations/:id/hosts`, and `/ride/gallery-items` all require a session.
- **Built the route file with the layout-route (`element`+`<Outlet/>`) shape from the start**, not the flat `<Layout>{children}</Layout>` wrapping the `ComingSoon` scaffold shipped with (and that `rcl.routes.tsx` still uses today). This was already identified and fixed for `mission3011`/`drishti` (see that section above) as a real bug - a flat wrap renders `RequireSubdomainAuth`'s sign-in prompt and `RequirePermission`'s forbidden state outside `SubdomainShell`, with no header/nav. RIDE has no reason to reintroduce it just because RCL's file happens to still have it.
- **No dedicated "dashboard" page.** Unlike Mission3011/Drishti, the spec's RIDE route list is only `/incoming`, `/support-club`, `/gallery`, `/admin` - no landing/summary page. The index route (`/`) renders `RideIncomingPage` directly rather than a placeholder or a redirect, since the incoming-delegations list is already the natural public landing view for this subdomain. The API's `GET /public/ride/dashboard` (delegations-this-RY / host-clubs-count summary) exists purely to back `ProjectSummaryRegistry` for the district Home page's project cards, not a RIDE-owned page - nothing in this repo fetches it directly.
- **Support-club registration (`SupportClubForm`/`SupportClubPage`) is a near-exact structural copy of RCL's `RegisterPage`/`TeamForm`** ("one registration per club per RY, POST upserts in place") rather than Mission3011/Drishti's submit-then-admin-reviews pattern, matching the API's own design call (support-club registration has no review step, just an officer-owned upsert).
- **Swapped `Combobox` for a plain `Select` on the optional "point of contact" field.** `Combobox` (used elsewhere for member-linking, e.g. RCL's `TeamForm`) renders its search input with no accessible name unless a `label` prop is threaded through by the caller - an existing gap in the shared component, not introduced here, just newly exposed because `SupportClubPage` renders its form unconditionally on load (Mission3011's/RCL's forms sit behind a button/modal, so axe never scans them at rest). A handful of club members doesn't need typeahead search, so `Select` sidesteps the gap entirely rather than patching the shared `Combobox` (out of scope, and risks affecting RCL's already-shipped usage). `MultiSelect` (used for "preferred months") has the same underlying gap but does expose a `label` prop that wires `aria-label` correctly - passed explicitly here, and worth passing anywhere else `MultiSelect`/`Combobox` render unconditionally in the future.
- **Gallery videos are rendered as a real `<iframe>` embed for recognized hosts (youtube.com/youtu.be/drive.google.com file links) via a small pure `videoEmbedUrl()` helper (`src/lib/ride/video.ts`, unit-tested), falling back to a plain "Watch video" link-out for anything else** - matches the spec's explicit host list and the "every asset field offers both Upload and paste-a-link" convention already established for photos (`FileUpload`/`AssetUrlField`). The e2e axe check for `/gallery` excludes `iframe` content from the scan (`AxeBuilder(...).exclude('iframe')`) since a real third-party embed's internal markup (YouTube's own player chrome) is not this codebase's to fix, and the alternative (mocking a fake host so it always hits the link-out fallback) would mean the iframe code path is never actually exercised by CI.
- **Public gallery API shape is `{items, years}`, not a per-year-grouped structure.** `GET /public/ride/gallery` returns every item (optionally filtered by `?year=`) plus the full distinct-years list in one response; `RideGalleryPage` builds the year `Tabs` client-side from `years` and filters `items` by the active tab locally. This avoids either a second request per tab click or the server pre-grouping into a shape the client would just have to re-flatten to render a grid.
- **Admin host-assignment uses a `Drawer` (side="right"), not a `Modal`** - the spec explicitly calls this "a host-assignment drawer," and unlike Mission3011's single-field reject reason, RIDE's assignment surface is a list (every registered support club, each with an inline days/members editor), which reads better in a side panel than a centered dialog. `RideDelegationsController`'s `PUT .../hosts` full-replace contract maps directly onto the drawer's local state: every registered club for the current RY is pre-seeded as a row (checked + populated if already a host on that delegation, unchecked otherwise), and "Save" always sends the complete set of currently-checked rows, matching "replaces set" exactly rather than diff-patching.
- **Delegation creation is a `Modal` (matching Mission3011/RCL's "log a camp"/"new fixture" pattern), separate from the host-assignment `Drawer`** - these are two independent admin actions (add a delegation vs. assign hosts to an existing one) and combining them into one panel would conflate "describe the visit" with "who's hosting it," which the API also keeps as two separate endpoints (`POST /ride/delegations` vs `PUT .../hosts`).
- **e2e persona (`e2e/fixtures/me.json`) gained `"subdomain:ride:manage": [{ "type": "project", "id": "ride" }]`**, following the drishti/rcl/careerbridge precedent - this repo's shared mock-server e2e setup only supports one persona/session, so each subdomain that wants a *positive* interactive admin e2e test (here: assigning a host from the drawer) has to add its own grant to the shared fixture. `mission3011` remains the one subdomain deliberately left ungranted, so it stays available as every other subdomain's negative-permission test target. RIDE's own negative test instead asserts `RequireSubdomainAuth`'s sign-in prompt for an anonymous (no-cookie) visitor on `/support-club` and `/admin` - a real, meaningful assertion that doesn't depend on the persona's specific grant set.
